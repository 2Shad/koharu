Koharu は使用する機能に必要なネイティブライブラリとモデルを取得します。リリース版の実行に CUDA や ROCm の完全な SDK は不要です。

## デバイスの選択

起動時に利用可能なバックエンドから共通の ML デバイスを選びます。Apple シリコンでは Metal、それ以外では対応状況に応じて CUDA、ROCm/HIP、Vulkan、CPU を使います。デバイスは Torch、llama.cpp、diffusion のすべてのランタイムがそのデバイス向けのパッケージを公開している場合にだけ選ばれるため、OS、ドライバー、モデルのバックエンドがすべて対応している必要があります。

<Tabs>
  <Tab title='NVIDIA'>
    Windows と Linux で CUDA 13.3 を利用できます。Koharu が CUDA デバイスを選ぶのは、ドライバーが
    CUDA 13.3 以降を報告し、GPU の compute capability が 7.5 以降の場合だけです。つまり Turing
    世代以降の GPU と R610 系以降のドライバーが必要です。NVIDIA
    の[対応表](https://docs.nvidia.com/datacenter/tesla/drivers/cuda-toolkit-driver-and-architecture-matrix.html)と[ドライバー](https://www.nvidia.com/en-us/drivers/)を確認してください。
  </Tab>
  <Tab title='AMD'>
    ROCm/HIP の対応は GPU、OS、ドライバーの組み合わせで決まります。対応する [AMD
    ドライバー](https://www.amd.com/en/support)をインストールしてください。必要な ROCm ランタイムは
    Koharu が自動取得します。プラットフォーム要件は AMD
    の[互換性表](https://rocm.docs.amd.com/en/docs-10.0.0/compatibility/compatibility-matrix.html)を参照してください。
  </Tab>
  <Tab title='Apple シリコン'>
    Apple シリコン搭載 macOS では、対応するローカル推論に Metal を使います。
  </Tab>
  <Tab title='Vulkan と CPU'>
    Windows と Linux では、ローカル翻訳、PaddleOCR-VL、FLUX.2 Klein、RORem などの llama.cpp と
    diffusion のモデルに Vulkan を使えます。Torch には Vulkan ビルドがないため、Vulkan
    しか使えない環境では検出、その他の OCR モデル、LaMa、AOT は CPU
    で動作します。アクセラレーターを初期化できない場合は CPU にフォールバックします。CPU 推論に GPU
    SDK は不要ですが、処理は遅くなります。
  </Tab>
</Tabs>

<Note>
  キャンバスは組み込み CEF WebView の WebGPU を使います。ML 推論が CPU でも、動作する WebGPU
  アダプターとグラフィックスドライバーが必要です。
</Note>

## Android

Android 版は検出、OCR、翻訳、インペイントをすべて端末上で実行し、初回リリースはオフラインで動作します。実行可能コードをダウンロードすることはありません。llama.cpp ランタイム（`libllama`、`libmtmd`）と LibTorch ランタイム（`libtorch_cpu`、`libkoharu-torch` とその依存ライブラリ）は APK に同梱され、アプリのネイティブライブラリディレクトリから読み込まれます。モデルの重みはデータとして通常どおり取得します。

### モバイル既定値

モバイルのパイプラインは同時に 1 つのステージだけを常駐させます。ステージの読み込み前に他のステージを破棄するため、ピークメモリは合計ではなく最大の単一モデルに収まります。既定値はコミック向けです。検出は Comic Layout YOLO26s（`balloon`/`text`/`frame` が吹き出し/テキスト/パネルに対応）、OCR は Manga OCR、インペイントは AOT です。1152px の RF-DETR Seg 2XL と LaMa も選択でき、PP-DocLayout-V3 は文書レイアウト向けに用意されています（テキスト領域のみコミックの契約に対応）。

### モバイル向けモデルプロファイル

端末の RAM クラスに合うプロファイルを選びます。翻訳は既定でテキストのみで、ビジョン用プロジェクターはビジョン経路を有効にしたときだけ読み込みます。端末の予算を超える読み込みは、後から失敗するのではなく、読めるエラーとして拒否されます。

| 搭載 RAM | 翻訳 | 検出 | OCR | インペイント | ピーク目安 |
| -------- | ---- | ---- | --- | ------------ | ---------- |
| 6–8 GB   | Gemma 4 E2B Q2_K_XL | PP-DocLayout / YOLO26s | PP-OCRv6 / MangaOCR | AOT | 約 3.5 GB |
| 8–12 GB  | Gemma 4 E4B Q2_K_XL | PP-DocLayoutV3 | MangaOCR / PaddleOCR-VL GGUF | AOT / LaMa | 約 4.5 GB |
| 12–16 GB | Gemma 4 E4B Q4_K_XL | RF-DETR Seg 2XL | PaddleOCR-VL GGUF / MangaOCR | LaMa | 約 5.5 GB |

### アクセラレーター

CPU デバイスは常に利用でき、`gpu_layers` は 0 で動作します。Vulkan は既定で無効で、構成ファイルの `android_vulkan` で有効にします（既定値は `false`）。

```toml
[runtime]
android_vulkan = true
```

Adreno の Vulkan/OpenCL は小規模なモデルでは CPU より遅いことが多く、不安定な場合もあります。モバイル向けの読み込みプロファイルはスレッド数を高性能コアの構成から決め、mmap と Q8 の KV キャッシュを使います。

ローカル翻訳は RAM クラスごとの読み込みプロファイルで動作します。同じ `[runtime]` セクションで `battery_saver = true` を設定すると、デコードとプロンプトのスレッド数が半分になり、プロンプトバッチが小さくなり、ピーク常駐予算が 25% 削減されます。スループットと引き換えに、より低温で低消費電力の実行になります。既定では無効です。1 ページあたりの遅延を最も小さくするには無効のままにしてください。

```toml
[runtime]
battery_saver = true
```

### ベンチマーク

端末上でハーネスを実行して 1 行ずつ記録します。

```sh
cargo run -p koharu-translator --bin bench -- --model <model.gguf> --quantization Q4_K_XL --cpu
```

参照端末ごとに 1 行を埋めてください。生の記録は `--json` で出力できます。

参照端末の行は、Gemma 4 E4B Q4_K_XL を使った 1 ページのローカル翻訳ベンチマークの実測値です。章全体の実行ではありません。22 ページの通し実行では翻訳中に 7.6 GB まで達し、`LOW_MEMORY` による終了はありませんでしたが、`RamClass::High` の目標である約 5.5 GB を超えています。端末の thermal sysfs が不正な値を返したため、温度は未計測です。

8 GB ミッドレンジ、12 GB ハイエンド、6 GB 下限の行は参照端末での計測待ちです。各セルを空欄のままにしているのは意図的で、翻訳の列は各 RAM クラスで想定するプロファイルであり、実測値ではありません。同じ 3 クラスは[対応デバイス表](/ja/installation#対応デバイス)にもまとめています。

| ---- | --- | --- | ------ | ---------------- | ---------- | ---------- | ---------- | ---- |

### パリティ検証

同じページで端末上の出力がデスクトップと一致するか確認します。まずプラットフォームごとにレポートを 1 つ記録します。

```sh
cargo run -p koharu-pipeline --bin parity -- --input <page-directory> --output android.json
```

同じページとモデルを使ってデスクトップ（`desktop.json`）と端末（`android.json`）でそれぞれ実行し、2 つのレポートを比較します。

```sh
cargo run -p koharu-pipeline --bin parity-diff -- desktop.json android.json
```

差分には検出ボックス、マスクのダイジェスト、OCR テキスト、翻訳が含まれます。参照端末でのパリティ結果はまだ公開していません。上記の実測値は翻訳と章全体の実行によるもので、パリティの結果ではありません。

## 取得されるデータ

| データ                                                | 必要になるタイミング               |
| ----------------------------------------------------- | ---------------------------------- |
| Torch、llama.cpp、diffusion、バックエンドのランタイム | 該当ランタイムの初期化時           |
| バージョンを固定したモデルの重み                      | 選択した処理モデルの初回使用時     |
| ローカル GGUF 量子化ファイル                          | そのファイルを選択して使用するとき |

Android では Torch と llama.cpp のランタイムパッケージはダウンロードされず APK に同梱され、取得するのはモデルの重みだけです。パッケージは macOS と Linux では OS キャッシュ内の `koharu/packages`、Windows では Koharu のインストールディレクトリ内の `store` ディレクトリに保存されます。プロジェクトは `Documents/Koharu`、設定は `~/.koharu/config.toml` に保存されます。[データの保存先](/ja/reference/data)も参照してください。

ダウンロードは一時領域で準備してからキャッシュへ公開します。中断した場合は次の起動やモデル使用時に再試行できます。

## メモリとモデルの常駐

ページ一覧の下部にあるリソース表示で、プロセスとシステムのメモリ、CPU 使用率、選択したデバイスの使用率とメモリを確認できます。モデルは初回使用時にロードされ、後続の段階でも使えるようロードされたままになります。段階がメモリ不足で失敗すると、Koharu は他の段階のモデルをアンロードしてその段階を一度だけ再試行します。設定を保存するとモデルはアンロードされ、次の実行時に再ロードされます。

まず中程度の量子化を選んでください。小さいファイルは通常メモリを節約できますが、品質との交換条件があります。ディスクに収まってもデバイスのメモリに収まるとは限りません。

起動に失敗したら配布先への接続とドライバーを確認し、一度再試行します。繰り返す場合は完全なエラーを保存して[トラブルシューティング](/ja/reference/troubleshooting)へ進みます。
