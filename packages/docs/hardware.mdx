Koharu downloads the native libraries and model files needed by the features you use. You do not need a full CUDA or ROCm SDK installation to run a release.

## Device selection

Startup chooses a shared ML device from the available backends: Metal on Apple silicon, then CUDA, ROCm/HIP, Vulkan, or CPU where supported. A device is selected only when the Torch, llama.cpp, and diffusion runtimes all publish a package for it, so the operating system, driver, and model backend must all support the selected path.

<Tabs>
  <Tab title='NVIDIA'>
    CUDA 13.3 support is available on Windows and Linux. Koharu selects a CUDA device only when the
    driver reports CUDA 13.3 or newer and the GPU has compute capability 7.5 or newer, which means a
    Turing-class or newer GPU with an R610-series or newer driver. See NVIDIA's [driver and
    architecture
    matrix](https://docs.nvidia.com/datacenter/tesla/drivers/cuda-toolkit-driver-and-architecture-matrix.html)
    and [driver downloads](https://www.nvidia.com/en-us/drivers/).
  </Tab>
  <Tab title='AMD'>
    ROCm/HIP support depends on the exact GPU, operating system, and driver. Install a compatible
    [AMD driver](https://www.amd.com/en/support). Koharu resolves its required ROCm runtime packages
    automatically. Check AMD's [compatibility
    matrix](https://rocm.docs.amd.com/en/docs-10.0.0/compatibility/compatibility-matrix.html) for
    platform requirements.
  </Tab>
  <Tab title='Apple silicon'>
    Koharu uses Metal for supported local inference on Apple-silicon macOS.
  </Tab>
  <Tab title='Vulkan and CPU'>
    Vulkan provides an accelerator option on Windows and Linux for llama.cpp and diffusion models,
    such as local translation, PaddleOCR-VL, FLUX.2 Klein, and RORem. Torch has no Vulkan build, so
    detection, the other OCR models, LaMa, and AOT run on CPU on a Vulkan-only machine. If no
    complete accelerator path initializes, Koharu falls back to CPU. CPU inference requires no GPU
    SDK and is slower.
  </Tab>
</Tabs>

<Note>
  The editor canvas uses WebGPU in the embedded CEF webview. It still needs a working WebGPU adapter
  and graphics driver when ML inference runs on CPU.
</Note>

## Android

The Android build runs detection, OCR, translation, and inpainting fully on-device, so the first release works offline. Android never downloads executable code: the llama.cpp runtime (`libllama`, `libmtmd`) and the LibTorch runtime (`libtorch_cpu`, `libkoharu-torch`, and its dependencies) are bundled in the APK and resolved from the app's native library directory. Model weights are data and download as usual.

### Mobile defaults

The mobile pipeline keeps one model stage resident at a time: before a stage loads, every other stage is evicted, so peak memory tracks the largest single model instead of the sum. Defaults favor the comic profile — detection is Comic Layout YOLO26s (its `balloon`/`text`/`frame` classes map onto the bubble/text/panel contract), OCR is Manga OCR, and inpainting is AOT. The 1152px RF-DETR Seg 2XL detector and LaMa stay selectable; PP-DocLayout-V3 is available for document-style pages, where only its text regions map onto the comic contract.

### Mobile model profiles

Pick the profile that matches the device's RAM class. Translation is text-only by default; the vision projector loads only when the vision path is enabled. A load that would exceed the device's budget is refused with a readable error instead of failing later.

| Device RAM | Translation | Detection | OCR | Inpaint | Peak budget |
| ---------- | ----------- | --------- | --- | ------- | ----------- |
| 6–8 GB     | Gemma 4 E2B Q2_K_XL | PP-DocLayout / YOLO26s | PP-OCRv6 / MangaOCR | AOT | ~3.5 GB |
| 8–12 GB    | Gemma 4 E4B Q2_K_XL | PP-DocLayoutV3 | MangaOCR / PaddleOCR-VL GGUF | AOT / LaMa | ~4.5 GB |
| 12–16 GB   | Gemma 4 E4B Q4_K_XL | RF-DETR Seg 2XL | PaddleOCR-VL GGUF / MangaOCR | LaMa | ~5.5 GB |

### Accelerators

The CPU device is always available and runs with `gpu_layers = 0`. Vulkan is off by default; opt in with `android_vulkan` in the configuration file (default `false`):

```toml
[runtime]
android_vulkan = true
```

Adreno Vulkan/OpenCL is frequently slower than CPU for small models and can be unstable. The mobile load profile derives the thread count from the performance-core topology and uses mmap with a Q8 KV cache.

Local translation runs under a per-RAM-class load profile. Setting `battery_saver = true` in the same `[runtime]` section halves decode and prompt threads, shrinks the prompt batch, and trims the peak resident budget by 25%, trading throughput for a cooler, lower-power run. It is off by default; leave it off for the lowest single-page latency.

```toml
[runtime]
battery_saver = true
```

### Benchmarks

```sh
cargo run -p koharu-translator --bin bench -- --model <model.gguf> --quantization Q4_K_XL --cpu
```

### Parity harness

Verify that on-device output matches desktop over the same pages. Record one report per platform first:

```sh
cargo run -p koharu-pipeline --bin parity -- --input <page-directory> --output android.json
```

Run it once on desktop (`desktop.json`) and once on the device (`android.json`) with the same pages and models, then compare the two reports:

```sh
cargo run -p koharu-pipeline --bin parity-diff -- desktop.json android.json
```

The diff covers detection boxes, mask digests, OCR text, and translations. No parity result has been published for the reference phone yet; the measured numbers above come from the translator and full-chapter runs.

## Downloads and caches

| Data                                                      | When it is needed                       |
| --------------------------------------------------------- | --------------------------------------- |
| Torch, llama.cpp, diffusion, and backend runtime packages | When their runtime is initialized       |
| Pinned or versioned model weights                         | On first use of the selected processor  |
| Local GGUF quantizations                                  | When you choose and use that model file |

On Android, the Torch and llama.cpp runtime packages are bundled in the APK rather than downloaded; only model weights are fetched. On macOS and Linux, packages live under the operating system cache directory in `koharu/packages`. On Windows, they live in the `store` directory inside Koharu's installation directory. Projects live under `Documents/Koharu`; settings live in `~/.koharu/config.toml`. See [data locations](/reference/data).

Downloads are staged before being published to the cache. Retry an interrupted download on the next launch or model use.

## Memory and model residency

The resource monitor in the page rail footer reports process and system memory, CPU usage, and the selected device's utilization and memory. Models load on first use and stay loaded for later stages. If a stage fails with an out-of-memory error, Koharu unloads the other stages' models and retries that stage once. Saving settings unloads models, so the next run reloads them.

Start with a moderate local quantization. Smaller files usually need less memory, with a possible quality trade-off. A model that fits on disk can still exceed device memory.

If startup fails, check network access to the package repositories, update the driver, and retry once. Capture the full error if it repeats and follow [troubleshooting](/reference/troubleshooting).
